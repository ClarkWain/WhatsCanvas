Z-buffer / Early-Z / Hi-Z / Stencil：3D 场景里"看得见谁"

同一屏幕像素上可能有 5 个三角形想画，最终显示哪一个？这个决定全部落在 深度缓冲（Depth Buffer / Z-buffer） 及其一堆兄弟机制上：Depth Test、Early-Z、Hi-Z、Stencil、透明排序……每一层都在替 GPU 省事。这个教程会带你看清 z 值到底存的是什么、为什么远景总在 z-fight、为什么"半透明玻璃"必须自己排序、以及 2D 场景（比如 WhatsCanvas）用什么替代方案。

1. z 不是线性的透视除法后深度精度前密后疏，远处 z-fighting 不是 bug 是数学。
2. GPU 越懒越快Early-Z 让还没跑 fragment shader 的像素直接扔掉；Hi-Z 让整块 tile 一次扔掉。

01 · 深度值到底是什么

屏幕像素背后那个 [0,1] 的 z

顶点在 clip space 做了透视除法后落到 NDC（-1..1），再线性映射到 [0,1] 存进深度缓冲。关键：这个数是 1/z 的线性函数，不是 z 的线性函数。结果就是"离相机越远，两个物体的深度差距越小"，远景总是打架。

横轴是相机距离 z（世界坐标），纵轴是最终写入 depth buffer 的值。橙色曲线是 near/far 生成的 1/z 映射——注意远端几乎是水平的：远处两个物体前后差 10 米也只对应几乎相同的 depth。

Depth = f(z)
z_ndc = (far + near) / (far - near) − 2·far·near / ((far - near)·z) depth = 0.5·z_ndc + 0.5

z 是 view-space 相机距离；ndc z 是 -1..1；depth 是 0..1（默认 OpenGL）。分子里有 −2·f·n/z——这就是那个"远处等间距 z 变化几乎无效"的元凶。

精度分布
near=0.1, far=1000 时： z ∈ [0.1, 1] 用了 depth [0, 0.9] z ∈ [1, 1000] 只剩 depth [0.9, 1]

近处 90% 的深度精度、远处 10%。这就是为什么 near 绝对不能设太小——把 near 从 0.1 改成 1，远端有效精度立刻翻十倍。

02 · Depth Test 基本流程

每个 fragment 到底怎么被"接纳"或"扔掉"

顶点着色器 → 光栅化 → fragment shader → depth test → color write。默认 GL_LESS：新 fragment 的 z 比已有的小才通过；通过后写入 color 与 depth。glDepthFunc 换成 GL_LEQUAL/GL_GREATER/… 就能玩天空盒、多 pass 累积等技巧。

左侧是提交 3 个 quad 的顺序（红→绿→蓝，深度 0.3/0.5/0.4），右侧是不同 depthFunc 下最终的可见结果。天空盒常用 GL_LEQUAL + z=1.0 覆盖背景。

GL 状态 
glEnable(GL_DEPTH_TEST);
glDepthFunc(GL_LESS);
glDepthMask(GL_TRUE);  // 允许写 depth
glClearDepth(1.0f);
glClear(GL_DEPTH_BUFFER_BIT);

半透明物体渲染前，一般把 glDepthMask(GL_FALSE)，通过读 depth 剔除背景但自己不写 depth——防止半透明层互相遮挡。

为什么默认 clear 是 1.0？初始 depth 设成最远端，任何后来的 fragment 都能通过 GL_LESS。
Reverse-Z 技巧：把 clear 设成 0.0、depthFunc 用 GL_GREATER、投影矩阵 near/far 互换——远处精度显著提升。3A 引擎标配。
03 · Early-Z 与 Late-Z

GPU 最喜欢的优化：连 fragment shader 都别跑

标准流水线是 fragment shader → depth test。但 GPU 会主动尝试把 depth test 提前到 fragment shader 之前——这样被遮挡的像素连着色都省了。一旦 shader 里有 discard、写 gl_FragDepth、或做 alpha-to-coverage，Early-Z 会自动禁用。

场景：先画一张巨大近处 quad（挡住 80% 屏幕），再画一个复杂的远处物体。柱状图是"跑 fragment shader 的像素数"——Early-Z 生效时只跑 20%，禁用时跑 100%。

什么会禁用 Early-Z？

  • discard / clip()：GPU 无法预知这个 fragment 到底会不会写 depth，得跑完 shader 才知道。
  • 写 gl_FragDepth：shader 决定 depth 值，硬件无法用插值 z 提前测。
  • alpha-to-coverage：mask 由 shader 输出的 alpha 决定。
  • 手动 layout(depth_greater/less)：可部分保留 Early-Z——告诉硬件"我保证只让 z 更远/更近"。
实战：做叶子/头发 alpha-test，先把 opaque pass 全画完（Early-Z 全开），再单独做 alpha-test pass；这样至少 opaque 部分省下大把 shader 开销。
04 · Hierarchical-Z（Hi-Z）

不看单个像素，看 tile 一次剔一大块

现代 GPU 把 depth buffer 组织成 8×8 或 16×16 的 tile，每个 tile 存"这块最远/最近的 depth"。三角形来的时候先与整块的 min/max 比较——比整块最近的还远？整块跳过，一个 fragment 都不跑。

背景是 depth buffer（越黑越近）。蓝色 tile = "min(depth) > 新 z"，可以整块剔除；橙色 tile = 需要逐像素测试。调 tile 大小可以看到粒度权衡：太大浪费剔除机会，太小 metadata 开销大。

tile 判决
if newTri.zMax < tile.zMin → 整块通过（tile 内全部剔背景） if newTri.zMin > tile.zMax → 整块拒绝（新三角形被遮完） otherwise → 逐像素 depth test

"newTri.zMax < tile.zMin" 意思是新三角形整块都比 tile 里目前所有已画的东西还要近——直接盖上去。反之则被完全挡住。

front-to-back 排序为什么关键：近处物体先画，Hi-Z 迅速填满小 z 值，远处物体来了就被整块整块剔掉。反过来先画远处 → Hi-Z 一开始很松，剔除率极差。
写 depth 会破坏 Hi-Z：fragment shader 手动写 gl_FragDepth 后，GPU 无法维持精确的 tile min/max，Hi-Z 通常回退到宽松估计或禁用。
05 · Stencil Buffer

一个每像素 8 位的整数，能做的事比你想的多

Stencil 就是每个像素挂一个 8-bit 整数 + 一个测试函数。听起来简单但用途极广：portal / 镜像、UI mask、outline、老式 shadow volume。它常常和 depth buffer 打包在同一张 texture（GL_DEPTH24_STENCIL8）。

三种典型用法：mask 用 stencil 写标记 → 只在标记内画后续内容；outline 用两次绘制（放大版 & 正常版）+ stencil 排除内部；portal 在圆内画不同场景，圆外不动。

Outline 常用 pass 
// Pass 1: 正常物体，stencil 写 1
glStencilFunc(GL_ALWAYS, 1, 0xFF);
glStencilOp(GL_KEEP, GL_KEEP, GL_REPLACE);
drawModel();
// Pass 2: 放大 5% 的模型，只画 stencil ≠ 1 的地方
glStencilFunc(GL_NOTEQUAL, 1, 0xFF);
glStencilMask(0x00);
glDisable(GL_DEPTH_TEST);
drawModelScaled(1.05);
glEnable(GL_DEPTH_TEST);
glStencilMask(0xFF);
WhatsCanvas 里的 stencil：clipPath 就是典型 stencil 用法——先把裁剪区域写到 stencil，后续所有 draw 都被这个 mask 限制。
不要滥用：stencil write 会禁用 Early-Z 的一些优化路径；简单矩形裁剪用 glScissor 更省事。
06 · 透明为什么必须排序

Depth Test 只处理 opaque，玻璃层要靠 CPU 排

透明物体的 blend 是 顺序敏感 的：C = α₁·C₁ + (1−α₁)·C₂——先 C₂ 打底再 C₁ 混合，vs 相反顺序，结果不一样。GPU 的 depth test 只会说"这个像素能不能画"，管不了"先画谁"。这就是为什么半透明物体必须 CPU 端 sort by z (far→near)。

三片彩色玻璃 α=0.5 叠在一起。错误顺序时近处玻璃先画，但因为它写了 depth，后来远处玻璃的 fragment 被 depth test 拒绝——远景消失。正确顺序：远→近，且 glDepthMask(FALSE)。

OIT (Order-Independent Transparency) 简介

CPU 排序开销大 + 排序在物体互穿插时无解。学术界方案：

  • Depth Peeling：多 pass，每 pass 提取"当前最近未处理"的一层，从近到远混合。N 层要 N 次绘制。
  • Weighted Blended OIT (McGuire 2013)：近似方案，一 pass 搞定，把 α 按深度加权，可视觉上不完美但足够 UI/粒子用。
  • Linked-list OIT：fragment 写入 per-pixel 链表，最后一 pass 排序合成。DX11+ 才好用。
07 · Z-fighting 与 polygonOffset

两个几乎共面的三角形在打架

两个物体在同一深度或差距小于 depth buffer 精度时，depth test 会时而选前时而选后，屏幕出现闪烁条纹。远处 + far 太大 + near 太小 = z-fight 灾难现场。修复：拉近 near、用 reverse-Z、或用 glPolygonOffset 主动推开一层。

两个同 z 的 quad。距离拉远 → 深度精度掉光 → 出现随机闪烁条纹。加 polygonOffset → 其中一个被推离一点点 → 稳定。这就是 shadow map / decal 常用技巧。

polygonOffset 公式
offset = factor · dz/dxy + units · r

dz/dxy 是 depth 相对屏幕方向的斜率（近似"三角形有多倾斜"），r 是可最小分辨的 depth 增量。factor 通常 1.0~2.0，units 1.0。斜率大的三角形自动多推，倾角小的少推——非常聪明的设计。

Decal 常用：贴在墙上的血迹、弹孔——geometry 和墙面共面。glPolygonOffset(-1, -1)（负值往近推）确保 decal 稳定在墙面前。
Shadow map 也用：light-space 深度贴图比较时加 bias（等价 polygonOffset），防止 self-shadowing acne。
08 · 2D 场景的 z-order

WhatsCanvas 这种纯 2D 库怎么处理"谁在上面"

2D 画布通常没有 depth buffer——就用画家算法（painter's algorithm）：按提交顺序从后往前画，后画的覆盖先画的。API 里没有 z-index，就是 draw call 的顺序决定层级。这就是为什么 context.save/restore + clipPath 那么关键——它们控制"这一段 draw 产生的像素受什么约束"。

3 个矩形按不同顺序绘制。拖动 slider 看每一步：先画背景，再画中层，最后画前景——这就是所有 2D 绘图库、包括 WhatsCanvas 的默认策略。

2D 库为什么不用 depth buffer？

  • 2D 场景通常物体少（几十~几千），排序开销可忽略。
  • Anti-aliasing 混合需要严格顺序——depth test 会破坏这个顺序。
  • 省一大块显存 & 带宽（1920×1080×4B ≈ 8MB depth）。

例外：Skia / WhatsCanvas 在超复杂 clip 嵌套时会内部用 stencil 或 sub-surface，把 clipPath 转换成 mask，本质是"局部 z-buffer 替代品"。

WhatsCanvas 具体做法：src/render/RenderContext.cpp 的 applyClipState 用 stencil 存 clip mask；DrawPath 按 command 顺序执行 = painter's algorithm。
