底层库协作：谁负责哪一段

前面几章其实是被几个著名的 C/C++ 库分段实现的：HarfBuzz、FreeType、stb_truetype、OpenGL。它们各管一段、首尾相接。这一章把整条流水线串起来，看清每个库吃进什么、吐出什么。

三个字体库，定位完全不同

初学者常把它们搞混。一句话区分：HarfBuzz 决定画哪些字形、画在哪；FreeType / stb_truetype 把字形变成像素；它们谁也不画到屏幕——那是 OpenGL 的事。

库管哪一段特点什么时候选它
HarfBuzz塑形（shaping）只做塑形，不栅格化；复杂文字支持最全需要正确排版阿拉伯/印度文/连字时（几乎都要）
FreeType解析字体 + 取轮廓 + 栅格化 + hinting功能最全、质量高，但体积大、API 复杂需要高质量渲染、hinting、多格式支持
stb_truetype解析 TTF + 取轮廓 + 栅格化单头文件、几百行、零依赖；功能少游戏/嵌入式/工具，要轻量、能接受简单效果
OpenGL / 图形 API上传纹理 + GPU 绘制不懂字体，只画带纹理的三角形最终把字形位图画到屏幕（第 8 章）
为什么常常是「HarfBuzz + FreeType」组合
HarfBuzz 算出字形索引和位置后，需要有人去取这些字形的轮廓并栅格化——这正是 FreeType 的活。事实上 HarfBuzz 本身就能用 FreeType 作为字体后端读取度量。浏览器（Chrome/Firefox）、Android、很多 Linux 桌面都是这个组合。轻量场景则换成 stb_truetype。

关键优化：字形图集（glyph atlas）

每帧都重新栅格化每个字形太慢了。实际做法是：第一次遇到某个字形时栅格化一次，把位图存进一张大纹理——图集（atlas）——并记下它在图集里的坐标。以后再用到这个字形，直接从图集里取，GPU 一次就能画很多字。

glyph.atlas
图集纹理 · 每个字形栅格化一次后缓存

要画一段文字时，排版引擎为每个字形查图集，拿到它的 (u, v, w, h) 纹理坐标，拼成一批带纹理的四边形，一次 draw call 交给 GPU。

  • 命中缓存：字形已在图集 → 直接取坐标，零栅格化。
  • 未命中：栅格化一次 → 塞进图集空位 → 记录坐标。
  • 不同字号 / 粗细算不同字形，各占图集一格。

分层是为了可替换
正因为每段职责清晰、接口是简单的数据（字形索引、位图、纹理坐标），你才能替换其中一层：把 FreeType 换成 stb_truetype，把 OpenGL 换成 Vulkan / Metal / WebGPU，而其它层几乎不用动。理解这条边界，比记住任何单个库的 API 都重要。

问：HarfBuzz 能把字直接画到屏幕上吗？

看答案

不能。HarfBuzz 只做塑形——输出「画哪些字形索引、各自放在什么位置」。它不取轮廓像素、不画屏幕。要变成像素得交给 FreeType / stb_truetype 栅格化，最后由 OpenGL 等图形 API 上屏。这是典型的「各管一段」分层。
