互动教学 · 命令录制 (Picture / DisplayList)

canvas.drawXxx(...) 到底是"现在画"，还是"先记下来"？

图形库里有一个反直觉的事实：你调用 canvas.drawRect(...) 时，通常不会立刻画到显存 —— 它只是把这条命令追加进一份"命令列表"。等到 endFrame() 或者你显式重放时才真正提交给后端。这份可暂存、可重放、可跨帧、可跨线程搬运的中间物，就是命令录制（在 Skia 里叫 SkPicture，在 Flutter 里叫 Picture，在 Chrome 里叫 DisplayList）。它是"UI 缓存 / RepaintBoundary / 树差分渲染"这一整套优化的基石。

1. 立即模式的假象 你写的每一行 drawXxx 看起来像立刻画到屏幕，实际上都是"追加一条命令"。
2. 命令列表能做的事 可倒放、可裁剪、可合并、可提前分析（如"这里有多少条命令"）、可跨线程转发。

这页要带你掌握的 5 件事

  • 为什么 2D 图形库都爱把 drawXxx 写成"追加命令 + 稍后回放"。
  • WhatsCanvas 的 Picture：录制哪些能录、哪些拒录（saveLayer / DPR 变更被拒）。
  • drawPicture vs drawPictureRasterized：一个直接回放命令，一个先烘到纹理。
  • Skia SkPicture、Cairo recording surface、Chrome DisplayList、Flutter Picture 的对齐。
  • 什么内容适合录、什么内容一录就跌坑。
01 · 先看差别

立即模式 vs 保留模式，同一段代码走两条时间线

同样是一段 canvas.drawRect(); canvas.drawCircle(); canvas.drawText();，立即模式是"每一句都直达后端"；保留模式是"每一句都进入命令队列"，直到你按 endFrame / 重放才交给后端。切换单选按钮，看这两条流水线的差别。

先看直觉 写 UI 的时候你看到的： canvas.drawRect(...); → 屏幕出现矩形？ 现实中的库大多是： canvas.drawRect(...); → cmdList.push_back(DrawRect{...}) canvas.endFrame(); → renderer.execute(cmdList)

"看起来像立刻画，其实是排队"是一次抽象。它让你用简单的 API 表达"我要画什么"，同时给库留出优化空间：合并、重排、缓存、跨线程。

为什么要"稍后"处理 1. 合批 (batching) → N 条 drawRect 合成 1 次 drawArrays 2. 重排 (reorder) → 同 blend mode 的凑一起，减状态切换 3. 缓存 (cache) → 同一段命令流可以打成 Picture 反复贴 4. 分析 (analyse) → 提前知道"这一帧一共 N 条 draw"

这就是 Skia / WhatsCanvas / QPainter GL 后端做的事：绘制 API 长得像 Immediate，内部实现是 Retained + 提交时优化。

"命令录制"是把这个内部产物变成一等公民 大多数库把命令列表藏起来。 一旦暴露给用户，就变成了 Picture / DisplayList： ▪ 可反复 replay 到不同 Canvas ▪ 可序列化到磁盘、传给别的线程 ▪ 可用它做"UI 局部重画"（RepaintBoundary）

Flutter 的整个渲染 tree 就是由 Picture 组成的；Chrome DevTools 的"paint layer flashing"看到的一个个色块，本质上是"这些区域各自一份 DisplayList"。

02 · 3 种"保留形态"

命令录制其实有 3 个层次，各自解决不同问题

① 帧内命令列表

只在一帧内暂存，endFrame 时提交给后端。用户看不见。

② Picture / DisplayList

用户可见的、可重放的命令包，跨帧存在。可以传给另一个 Canvas。

③ Picture + 光栅缓存

Picture 第一次执行时烘成一张纹理，之后每帧是"贴一张纹理"。

① 帧内命令列表

这是几乎所有 2D 图形库都有的第一层。canvas.drawRect(...) 在这里就是"往一个 std::vector<Command> 里 push"。endFrame() 时 Renderer 遍历这份列表，做合批 / 重排 / 提交。你以为的立即模式其实是这一层在给你演戏。

      03 · 你的命令流长什么样

      点右边的按钮"画东西"，左边实时打印录制到的命令

      右侧点击按钮时，左侧 canvas 不会立刻画。命令都进入下方"命令流"日志。按"submit (endFrame)"才真正执行。这个模拟对应 src/render/DrawList.h / src/render/CommandDrawListEncoder.h：Canvas 层把语义化命令记下来，Renderer 层再把它们编译成一批 GPU draw call。

      观察：你会看到"save / rotate / drawRect / restore"这组是4 条独立的命令，不是一个语义原子。Renderer 内部会看到全部 4 条，并可以在合适时刻合并优化。这也是为什么"命令列表"比"保存 UI 树"更贴近 GPU。
      04 · WhatsCanvas Picture

      用户可见的命令包：recordPicture / drawPicture / drawPictureRasterized

      public API 在 include/wsc/Canvas.h 和 include/wsc/Picture.h：

      // 1. 把一段绘制录成 Picture
auto picture = canvas.recordPicture([](wsc::Canvas &c) {
    wsc::Paint p; p.setAntiAlias(true);
    p.setColor(wsc::Color(40, 120, 240, 255));
    c.drawRoundRect(wsc::RectF(20, 20, 200, 120), 12.0f, p);
    // ...几百条命令都可以录进去...
});

// 2. 直接重放（每帧都要重新走一遍命令）
canvas.drawPicture(*picture);

// 3. 或走光栅缓存：第一次烘成纹理，之后每帧只 blit
canvas.drawPictureRasterized(*picture);

// 4. 配置光栅缓存字节预算（0 = 禁用）
canvas.setRetainedPictureRasterCacheBudgetBytes(16 * 1024 * 1024);

      规则细节（写在 include/wsc/Picture.h 顶部注释）：

      // Picture ONLY owns CPU-side drawing inputs.
// 不占用 GPU 纹理 / command buffer，可以在 context 重建后照样 replay。
//
// recordPicture 的 recorder callback 是同步执行的。
// 依赖后端状态的操作会拒绝录制：
//   ✘ saveLayer         （需要一张后端纹理）
//   ✘ 变更 DPR         （改变了坐标空间基线）
// 一旦这些出现在 recorder 里，recordPicture 返回空 shared_ptr。

      这几条限制并非"图省事"，而是保证 Picture "backend-neutral": 一份录出来的 Picture 可以放到 Software 后端 replay，也可以放到 OpenGL / Vulkan 后端 replay，结果一致。

      drawPicture 直接重放

      把 Picture 里存的所有命令逐条重新提交给当前帧的 Renderer。适合"命令不多、但形状可能每帧微调"（如可缩放的图表）。

      drawPictureRasterized 光栅缓存

      首帧：把 Picture 烘成一张离屏纹理并缓存。后续帧：只 drawImage 那张纹理。适合大量命令、内容基本不变的场景（背景层、静态图表）。
      内部走 setRetainedPictureRasterCacheBudgetBytes 定的字节预算，超预算就 LRU 淘汰。

      不能录 saveLayer

      要一张后端纹理，破坏 backend-neutral 承诺。想在录制里达到"分组透明"的效果，就把这段单独抽出来，用父 Canvas 上的 saveLayer 包住 drawPicture。

      不能录 setDevicePixelRatio

      会改变逻辑单位到物理像素的映射。录出来一份 DPR=2 的 Picture，放到 DPR=3 的 Canvas 上就完全对不齐。要按 DPR 分别录制。

      三种模式：不录、drawPicture、drawPictureRasterized

      FPS 近似 —

      同一场景（一堆固定背景 + 一些动画物体）用 3 种方式画。观察"每帧后端命令数"如何变化：不录 = 全部命令都要重传；drawPicture = 命令数不变，但 Canvas 层省了各种 hash + state 检查；drawPictureRasterized = 每帧只 1 次纹理 blit + 少量动画命令。

      收益怎么看 不录 (immediate) ≈ 基线 drawPicture ≈ 基线 × 0.6~0.9 （省的是 Canvas 层的开销） drawPictureRasterized ≈ 1 次 blit + Δ （省的是所有底层绘制）

      "Δ"是那些不能录进 Picture 的部分（动画层、saveLayer 等）。所以 rasterized 收益上限 = "静态命令 / 总命令" 的比例。静态越多，收益越大。

      坑：只有极少变化就整块重烘 Picture 缓存，是错的方案 —— 它是设计给"完全不变"的层。局部变化频繁时要把变化的部分拆到父 Canvas 里画，静态部分留在 Picture 内。
      06 · WhatsCanvas 内部

      三段真实代码：Picture、DrawList、Command 编码器

      1. Picture 是 CPU-only 的命令快照 —— include/wsc/Picture.h

      class WSC_API Picture final {
public:
    std::size_t operationCount() const;
    bool empty() const { return operationCount() == 0; }
private:
    friend class Canvas;
    struct Impl;                          // pimpl —— 内部才知道命令类型
    explicit Picture(std::unique_ptr<Impl>);
    std::unique_ptr<Impl> impl_;
    // 拷贝/移动都 delete —— Picture 是共享的不可变值，
    // 用 std::shared_ptr<const Picture> 传递。
};

      2. 每一帧的命令流是一个 std::vector<Command> —— src/render/DrawList.h

      // 简化的形态：
struct DrawList {
    std::vector<PrimitivePacket> primitives;   // 编码后的 draw call
    std::vector<UniformBlob>    uniformStorage; // 打包好的 uniforms
    // 其他: index buffer、纹理绑定表、scissor / clip 状态...
};

// 每次 endFrame:
//   1) 前端: 把 std::vector<Command> 编码成 DrawList
//   2) 后端: 把 DrawList 转成 backend-specific 提交

      3. 从 Canvas 命令到 DrawList 的编码器 —— src/render/CommandDrawListEncoder.h

      class CommandDrawListEncoder {
public:
    // 输入: Canvas.commands_（std::vector<std::unique_ptr<Command>>）
    // 输出: DrawList，可直接喂给 RenderDevice
    DrawList encode(const std::vector<std::unique_ptr<Command>> &commands,
                    const EncodeRequest &request);
    // request 里带上 canvasWidth/canvasHeight/createClipMaskTexture 等
};

      这就是"内部命令列表"到"backend-ready DrawList"的桥。合批、重排、mask 提交都发生在这里。

      1. Canvas 层：语义化命令 DrawPathCommand{data}、DrawImageCommand{data}、DrawTextCommand{data}——它们记录"你想画什么"，不关心怎么变成 GPU draw call。
      2. Renderer 层：编码 + 合批 CommandDrawListEncoder 会把连续多条 DrawPathCommand（相同 blend / clip / paint）合并成一个 PrimitivePacket，把 image draw 集中到 SpriteBatch。
      3. Backend 层：真正提交 OpenGLRenderDevice::executeDrawList（或 Vulkan / Metal 对应实现）把 DrawList 变成一组 glBindBuffer + glUseProgram + glDrawElements。
      Picture 到底是在哪一层？ 在 Canvas 层的上游。recordPicture 用一个"影子 Canvas"接住 recorder 的所有 drawXxx，把它们打包放进 Picture::Impl。drawPicture(picture) 时相当于"把影子里的操作 flush 到真的 Canvas 上"，再走一次完整 encode → execute。
      07 · 主流做法

      Skia、Cairo、Chrome、Flutter、Qt 里对应的东西

      Skia

      SkPicture + SkPictureRecorder。可 serialize() 到二进制传输，也可以 approximateOpCount() 提前分析。SkPictureShader 甚至能把 Picture 当着色器用。

      Cairo

      cairo_recording_surface_create：所有 cairo_* 命令都可以录到一个 cairo_surface_t 里，之后 cairo_set_source_surface 回放。是最早引入"命令录制"的 2D 库之一。

      Chrome DisplayList

      Blink 把每个 layer 的绘制命令录成 PaintOpBuffer（内部叫 display item list），由 compositor 决定何时 rasterize。开发者工具里的 "paint flashing" 显示的就是这些。

      Flutter Picture

      Flutter 的整个渲染管线就建立在 ui.Picture 上。PictureRecorder → 一份 Picture → SceneBuilder.addPicture() 塞进场景。RepaintBoundary widget 决定"这里另起一份 Picture 供缓存"。

      Qt QPicture

      QPainter 的 QPicture 是一份可序列化到 QPictureFormat 的绘制脚本。QML 场景图（QSGRenderNode）则是更贴近 GPU 的 retained scene，功能更全但抽象更高。

      浏览器 Canvas 2D

      W3C API 没有直接暴露 Picture，但你可以自己拿一个 <canvas> 当"录制器"：先画一遍，再 drawImage(thatCanvas, ...) 到别的 canvas 上——这就是最土的"用户级 Picture"。

      共同点：所有库都区分"发出命令"和"执行命令"两个阶段。命令录制就是把这个内部阶段变成用户可持有的一等对象。
      不同点：WhatsCanvas 的 Picture 是严格 backend-neutral——不能录 saveLayer。Skia SkPicture 允许 saveLayer，但代价是重放时必须绑定一个特定 GPU context。WhatsCanvas 的取舍偏"简单可靠"。
      08 · 你可以怎么判断

      什么时候该录 Picture、什么时候不该录

      命令数多、内容不变推荐 drawPictureRasterized 静态背景、地图瓦片、复杂图表的底层。每帧 1 次 blit 代替上千条 draw。收益最直接。
      命令数多、内容频繁变看情况 每帧全变没意义（缓存 miss 100%）；但如果只是颜色 / 位置变、结构不变，可以拆成"结构 Picture + 主 Canvas 每帧调 setTransform / drawImage"。
      需要合成透明层 / 滤镜避免直接录 Picture 里不能录 saveLayer。正确姿势：Picture 只录"层内的绘制"，saveLayer 留在父 Canvas 里包住 drawPicture。
      要跨线程 / 跨进程搬运推荐 recordPicture Picture 只吃 CPU 内存，可以在线程 A 录、线程 B replay（同 Renderer/context）。Flutter 就是这么做多线程渲染的。
      只画几十条命令、每帧都不同不要录 Picture 本身有分配 + 遍历成本，收益抹平后还倒亏。留在普通 Canvas 上直接画即可。
      一句话总结 命令录制 = 把"绘制"和"执行"两个阶段解耦， 让绘制的结果（不是像素，而是命令流） 可以被存起来、算作值、跨线程搬运。 命令流上的每一次优化（合批 / 重排 / 缓存 / 跨帧复用） 都比"每次到达 GPU 才优化"更早、更便宜。

      这条原则贯穿 Skia、Flutter、Chrome、WhatsCanvas。理解了"命令录制"，你就理解了现代 2D 渲染管线里"为什么这么多层"。
