互动教学 · 栅格化与缓存

三角形怎么变成像素？谁在偷偷帮我们省下这一步？

2D 图形库从一堆 drawRect / drawPath 命令走到"屏幕上的像素"其实要过两道关：先做栅格化（决定"哪些像素被覆盖，覆盖多少"），再做各种缓存（避免每帧都从头算一遍）。这个教程会带你看清：栅格化到底怎么算、Software 与 OpenGL 后端各自把栅格化放在哪儿、WhatsCanvas 里有哪些缓存（tessellation、glyph atlas、render target pool、picture cache），以及它们分别在解决什么问题。

1. 先算像素 栅格化 = 判定每个像素是否在几何图形内 + 它被覆盖多少。
2. 再省算 缓存不改结果，只改"要不要再算一次"。命中一次省下的往往是几百条命令。

这页要带你掌握的 5 件事

  • 栅格化的 3 种做法：扫描线、边函数（Edge Function）、GPU 三角形装配。
  • WhatsCanvas 里 CPU 光栅器怎么写：三角形 barycentric + top-left 规则。
  • 为什么 GPU 后端要靠 LruCache 缓存 tessellation 结果。
  • Glyph Atlas、RenderTargetPool、Picture Cache 各自解决哪种"重复计算"。
  • 什么时候该主动加缓存、什么时候缓存反而更慢。
01 · 先看本质

三角形是怎么"落到像素网格"上的？

对一个 CPU 光栅器来说，处理三角形的核心就是 3 个"边函数"：edge(A,B,P) = (B.x-A.x)(P.y-A.y) - (B.y-A.y)(P.x-A.x)。三个边函数同号 → 像素在三角形内；靠近 0 → 刚好在边界。上图把每个像素分类为"内 / 外 / 边界"，你可以调节网格粒度，看粒度变粗时锯齿如何变得明显。

先直觉：边函数在算什么 从 A 到 B 画一条有向线段， 把点 P 放到线段左边 → edge > 0 把点 P 放到线段右边 → edge < 0 点 P 正好在线段上 → edge = 0

这就是"从 A 走到 B 时，P 在你的左手边还是右手边"。三角形有 3 条有向边（A→B, B→C, C→A），如果 P 在这 3 条边都在"同一侧"，那 P 一定在三角形里面。

再看公式 edge(A, B, P) = (B.x − A.x) × (P.y − A.y) − (B.y − A.y) × (P.x − A.x)

前半 (B.x−A.x) 和 (B.y−A.y) 是"A→B 这条向量的分量"；后半 (P.y−A.y) 和 (P.x−A.x) 是"A→P 这条向量的分量"。整个式子就是两个二维向量的叉积——叉积告诉你右手系里旋转的方向，也顺便告诉你 P 在 AB 的哪一侧。

一个具体例子 A = (0, 0), B = (4, 0), P = (2, 1) edge(A, B, P) = (4−0) × (1−0) − (0−0) × (2−0) = 4 × 1 − 0 × 2 = 4 → 正数，P 在 A→B 的"上方"（y-down 系里就是上边）

如果把 P 换成 (2, −1)，结果就是 −4（P 在 A→B 的下边）。数字的绝对值是"两个向量张成的平行四边形面积"——这也是它同时能算面积的原因。

3 个边函数同号 ⇔ 在三角形内 对 A, B, C 这 3 个顶点按逆时针顺序： e0 = edge(B, C, P) e1 = edge(C, A, P) e2 = edge(A, B, P) 若 e0, e1, e2 都 ≥ 0 → P 在三角形内 若有一个 < 0 → P 在外面

直觉上：把三角形三条边都当"墙"，你从每堵墙的哪一侧看到 P？如果 3 堵墙都从"内侧"看到 P，P 就一定在屋里；只要有 1 堵墙从"外侧"看到 P，P 就在屋外。这也是为什么这个方法叫"parallel edge algorithm"——3 条边可以完全独立地判断，不需要维护"扫描线到边缘的进出状态"。

移动鼠标到三角形里，看 3 个"重心坐标"如何变化。它们分别是"P 离 3 个顶点各有多近"的权重。3 个数加起来永远等于 1；在顶点处会有 1 个是 1、另外两个是 0；在三角形中心 3 个都是 1/3。

重心坐标（Barycentric） b0 = edge(v1, v2, P) / area b1 = edge(v2, v0, P) / area b2 = edge(v0, v1, P) / area area = edge(v0, v1, v2) ← 三角形面积 × 2 b0 + b1 + b2 = 1 （恒等）

你已经知道 edge(v1, v2, P) 是"v1→v2 这条边和 P 组成的小三角形"的 2 倍面积。所以 b0 = 那个小三角形面积 / 三角形总面积——这就是"P 相对 v0 的权重"（因为对面的边 v1v2 张成的小三角形越大，说明 P 离 v0 越近）。

它有什么用？"三合一插值器" 任何在顶点定义的属性 X（颜色、纹理坐标、覆盖度）： X(P) = b0 × X(v0) + b1 × X(v1) + b2 × X(v2) 举个例子： v0 红色 (255, 0, 0) v1 绿色 (0, 255, 0) v2 蓝色 (0, 0, 255) P 在中心 (b0=b1=b2=1/3) → 颜色 = (85, 85, 85) 灰色

这就是 GPU 从顶点数据"渐变"到像素的秘密。GLSL 里 varying / in 变量自动做这个插值，你不需要显式写重心坐标，硬件光栅器把它塞进去。抗锯齿的 coverage 也是同样办法：3 个顶点各有一个 float coverage（内部三角形都是 1.0，fringe 三角形是 1.0 或 0.0），barycentric 插值出来就是每个像素的 alpha 系数。

联结：你会发现"边函数"和"重心坐标"其实是同一件事的两种视角——
边函数 回答"在里面吗"（符号）； 重心坐标 回答"离每个顶点多近"（比例）。 它们的分子都是同一批 edge() 计算的结果——CPU 光栅器算一遍就都拿到了。
02 · 3 种做法

扫描线、边函数、GPU 三角形装配的取舍

扫描线（Scanline）

逐行处理：对每一条扫描线求出多边形的进入/退出 x 坐标，中间平面填充。

边函数（Edge Function）

逐像素判定：每个像素代入 3 个边函数，同号 → 在内。适合并行，易 SIMD 化。

GPU 硬件装配

顶点着色器输出的裁剪空间三角形，交给固定管线的光栅化硬件，一个 fragment shader 一个像素。

扫描线（Scanline）

最经典的 CPU 光栅化算法，尤其适合任意封闭多边形（不只是三角形）。对每条水平线维护 Active Edge Table，找到进入 / 退出多边形的 x 坐标，然后填中间。stb_truetype 等字体光栅器还在用它的变体。

      03 · 覆盖度

      "是否在内"不够，还要"覆盖了多少"

      同一个三角形，用三种"覆盖度"方式渲染：二值判定（0/1 硬边）、4×4 子采样、解析式覆盖度（沿边缘生成 1 像素羽化带 + 顶点覆盖度插值）。WhatsCanvas 走的是第三种——参见 src/canvas/Canvas.cpp: expandTrianglesWithAA。

      为什么 WhatsCanvas 选解析式 SSAA / MSAA 需要 4-8 倍带宽； 后处理 AA 需要额外的 pass； 解析式 = "几何再多长出一带，顶点带 coverage" — 不吃采样成本，Software / GL / Vulkan / Metal 后端全部同一路径。

      Software 里 coverage 直接在 rasterizeTriangles 里用 barycentric 插值；GL 里传成一个顶点属性，在 fragment shader 里乘 alpha。

      相关代码： src/canvas/Canvas.cpp: expandTrianglesWithAA 沿轮廓扩边生成 fringe 三角形； src/opengl/ClipCoverageProgram.cpp 用同样思路生成裁剪路径的 R8 掩码； src/render/software/SoftwareRenderer.cpp: rasterizeCoverageTriangles 是 CPU 版本，缺 per-vertex coverage 时 fallback 到 1.0（本仓库 1.2.1 修复了 OpenGL 端漏掉这个 fallback 的 bug）。
      04 · 缓存分类

      WhatsCanvas 里的 4 层缓存各自解决什么

      ① Tessellation Cache

      把 path → 三角形列表这一步的结果缓存。反复画同一个圆角矩形时省下三角化。

      ② Glyph Atlas

      字体光栅化很贵。把常用字形烘到一张纹理里，绘制变成"贴几张四边形"。

      ③ Render Target Pool

      saveLayer / 离屏合成需要一次性大量创建 FBO+纹理。池化它们，避免频繁 GL 申请。

      ④ Picture Cache

      把一段"很少变的绘制命令"录成 Picture 一次性栅格化到纹理，之后每帧只贴一次。

      ① Tessellation Cache

      路径先要拆成三角形才能给光栅器。这一步在 CPU 上做一次很便宜（微秒级），但一秒 60 帧 × 上百个形状 × 反复重画同一个形状 = 每秒几万次三角化，成本就上来了。LruCache<FillTriangles>（src/render/LruCache.h）按 hash(path shape) 做键，命中就复用；容量按条目数和常驻字节两条边同时约束，避免"某一次超大 path 撑爆缓存"。

          把缓存关掉再打开，看 fps / 每帧工作量的变化

          tessellation 计算次数 —
          glyph 光栅化次数 —

          每帧总工作单位 —

          把三个缓存分别关闭 / 打开，看"每帧总工作单位"如何变化：一次 tessellation ≈ 3 单位，一次 glyph 光栅 ≈ 5 单位，一次纹理 blit ≈ 1 单位。真实数字取决于形状、字号、GPU 性能，但相对关系是稳定的。

          经验公式 缓存收益 ≈ ( 命中率 × 单次命中省下的工作 ) − 缓存自身开销 单次命中省下的工作 = 原始计算成本 缓存开销 = hash 计算 + LRU 更新 + 内存 footprint

          这就是为什么"只跑一次的 path"或"每次都不一样的动画路径"不适合走缓存——命中率太低，反倒被 hash 拖慢。

          观察：把形状数量拉到 800，关掉 tessellation cache，看看每帧总工作单位怎么冲高；再打开它，工作单位立刻下降到 命中率 × 原开销 的水平。
          06 · WhatsCanvas 内部

          三段真实代码：LRU、RenderTargetPool、Software 光栅

          1. LruCache 双约束（条目数 + 字节数） —— src/render/LruCache.h

          template <typename Value, typename Key = std::uint64_t>
class LruCache {
  const Value *find(const Key &key);   // 命中时 splice 到最新
  const Value &insert(Key key, Value v); // 超预算 → evictOldest
private:
  std::size_t maxEntries_;
  std::size_t maxResidentBytes_;
  std::list<Entry> order_;              // 头新，尾旧
  std::unordered_map<Key, iter> index_;
  std::size_t residentBytes_ = 0;
  std::size_t hitCount_ = 0, missCount_ = 0;
};

          典型用户：fillTessellationCache、clipAaCache、fillAaCache，键都是 path 或几何形状的 FNV hash。

          2. RenderTargetPool 复用离屏 FBO —— src/render/RenderTargetPool.h

          class RenderTargetPool {
  std::unique_ptr<IRenderTarget> acquire(int w, int h);
  void release(std::unique_ptr<IRenderTarget> target);
  void expire(int maxIdleCycles = 64);
  static constexpr size_t kDefaultMaxPooledBytes = 32u * 1024u * 1024u;
};

          预算 32 MiB + 每 target 4 KiB 开销估算。saveLayer 频繁进出时不再每次都申请纹理。

          3. CPU 光栅化的核心循环 —— src/render/software/SoftwareRenderer.cpp

          for (int py = minY; py <= maxY; ++py) {
  for (int px = minX; px <= maxX; ++px) {
    const float sx = px + 0.5f, sy = py + 0.5f;
    const float e0 = edge(v1.x, v1.y, v2.x, v2.y, sx, sy);
    const float e1 = edge(v2.x, v2.y, v0.x, v0.y, sx, sy);
    const float e2 = edge(v0.x, v0.y, v1.x, v1.y, sx, sy);
    const bool in0 = e0 > 0 || (e0 == 0 && tl0);  // top-left rule
    // 3 个都在内 → 用 barycentric 插值 coverage / color
  }
}

          top-left 规则保证共享边缘的两个三角形恰好由其中一个覆盖。同一条边永远不会被 blend 两次。

          1. 命中一次省下多少？ Tessellation cache 命中 ≈ 省 40-200 μs（复杂 path）；Glyph atlas 命中 ≈ 省一次 FreeType/DirectWrite bitmap 光栅 ≈ 100-800 μs；Picture cache 命中 ≈ 省几十至上千条命令的完整重放。
          2. 命中率怎么看？ LruCache 自带 hitCount_ / missCount_ / evictionCount_，通过 CanvasStats 曝光。命中率长期低于 30% 时说明缓存边界没选对（key 太宽 / 太窄），要看 hash 里带没带上必要维度。
          3. 缓存的失效器 动画参数变化（每帧不同 path） / 尺寸变化（每次缩放都是新 hash） / 显示器 DPR 切换 / 主动 clear()。同时字体大小上升 1 个 pixel 也会让 glyph atlas 完全 miss。
          07 · 主流 2D 图形库怎么做

          Skia、Cairo、Qt、浏览器 Canvas 各自的栅格化 + 缓存策略

          Skia

          CPU 侧 SkAAAnalyticEdge 解析式覆盖度；GPU 侧走"triangulation + coverage"或 stencil-and-cover。Glyph 走 SkGlyphCache，路径三角化结果按 GPU device 侧的 GrPathCache 缓存。

          Cairo

          典型的扫描线 + 覆盖度（AA_DEFAULT / AA_BEST 走软件抗锯齿）。缓存较轻，主要用 cairo_glyph_t 内部字形缓存，绘制路径本身没有强 shape 缓存。

          Qt / QPainter

          软件后端走扫描线；OpenGL 后端 QOpenGLPaintEngine 用 stencil-fill 或 triangulation。文字通过 QTextureGlyphCache。QML 场景图有"批处理 + 层"两级缓存。

          浏览器 Canvas 2D

          Chrome/Safari 底下都跑 Skia。字体走各自平台的 glyph rasterizer + atlas。用户几乎接触不到"缓存开关"，但 ctx.drawImage(anotherCanvas, ...) 就是最典型的"用户主动做 picture cache"。

          共同点：所有主流库都同时依赖几何缓存（tessellation 或 coverage）+ 纹理缓存（glyph atlas），因为这两类计算最容易在动画里重复。
          不同点：抽象层次不一样。Skia 提供 Grcache / Picture 给用户手动缓存；Qt/Cairo 只做内部缓存；浏览器 Canvas 让用户显式用 OffscreenCanvas 或多个 canvas 层管理。
          08 · 你可以怎么判断

          什么时候值得给一个绘制加缓存

          命中率 > 70% 才有意义推荐 反复出现的 UI 元素（按钮、图标、卡片背景、图表格线）、每帧都需要重画但形状不变的部分。这类命中率往往 > 90%，收益最直接。
          命中率 30-70% 视情况看开销 缓动动画、少量参数变化的形状。要看 hash key 是否合理——把非本质字段带进 key 会让命中率崩到 10%。
          命中率 < 30% 不要用避免 完全随机形状、每帧尺寸都不同的元素、只出现一次的复杂 path。hash + 内存开销会超过原本的计算成本。
          灰色地带：saveLayer + filter谨慎 每个 saveLayer 都会去 RenderTargetPool 拿一张同规模纹理。频繁进出层且尺寸抖动会击穿池；配合 expire(maxIdleCycles) 才能真正回收。
          一句话总结 栅格化 = 每一像素都要算的"必修课"； 缓存 = 让重复的路径可以跳课。 关键在于"命中率"和"单次命中省下的工作"， 两个都要够高，缓存才值得存在。

          Software 后端的核心是逐像素 barycentric + top-left；GPU 后端的核心是 tessellation + 顶点属性 + 硬件光栅。缓存并不改变这条路径，只是让它少走几次。
