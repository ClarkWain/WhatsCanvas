字字体渲染原理
CHAPTER 10 · CODE BY EXAMPLE

三大库代码示例：stb_truetype / FreeType / HarfBuzz

前面第 7 章讲了这三个库「各自负责哪一段」，这一章直接上代码，看每个库到底怎么调用。例子都精简到「最少能跑通」的程度，重点是看清每一步在做什么，而不是写一个完整项目。

先回顾分工
stb_truetype：单头文件，最简单，自己读 TTF + 栅格化，适合小项目 / 游戏。 FreeType：工业级栅格化引擎，质量高、hinting 全，几乎所有系统都在用。 HarfBuzz：只管塑形（字符序列 → 字形序列 + 位置），不画像素，常和 FreeType 搭配。
code.examples

目标栅格化 · 极简：把字符 'A' 渲染成一张灰度位图，直接能当纹理用。整个库就一个头文件。

#define STB_TRUETYPE_IMPLEMENTATION
#include "stb_truetype.h"

// 1. 把字体文件整体读进内存
unsigned char *ttf = read_file("Roboto.ttf");
stbtt_fontinfo font;
stbtt_InitFont(&font, ttf, stbtt_GetFontOffsetForIndex(ttf, 0));

// 2. 计算缩放：让字高 = 48 像素
float scale = stbtt_ScaleForPixelHeight(&font, 48.0f);

// 3. 直接把 'A' 栅格化成 8-bit 灰度位图
int w, h, xoff, yoff;
unsigned char *bitmap =
    stbtt_GetCodepointBitmap(&font, 0, scale, 'A',
                             &w, &h, &xoff, &yoff);

// 4. bitmap 是 w*h 的「覆盖率」(0-255)，上传当纹理即可
upload_texture(bitmap, w, h);

stbtt_FreeBitmap(bitmap, NULL);

关键点：stbtt_GetCodepointBitmap 一步到位——它内部完成了「查 cmap → 取轮廓 → 栅格化」。返回的就是每个像素的灰度覆盖率，可直接作为 alpha 上传到 GPU。胜在零依赖、一个文件，缺点是 hinting / 复杂排版能力弱。

目标栅格化 · 工业级：用 FreeType 把 'A' 渲染成高质量灰度位图，并拿到度量信息（偏移、advance）。

#include <ft2build.h>
#include FT_FREETYPE_H

FT_Library lib;
FT_Init_FreeType(&lib);

FT_Face face;
FT_New_Face(lib, "Roboto.ttf", 0, &face);   // 加载字体
FT_Set_Pixel_Sizes(face, 0, 48);            // 字高 48px

// 加载字符 'A'，FT_LOAD_RENDER 顺带栅格化
FT_Load_Char(face, 'A', FT_LOAD_RENDER);

FT_GlyphSlot g = face->glyph;
// g->bitmap.buffer / width / rows  →  位图数据
// g->bitmap_left, g->bitmap_top    →  相对笔位的摆放偏移
// g->advance.x >> 6                →  前进宽度(1/64 像素 → 像素)
upload_texture(g->bitmap.buffer,
               g->bitmap.width, g->bitmap.rows);

FT_Done_Face(face);
FT_Done_FreeType(lib);

关键点：FreeType 把「加载」和「渲染」拆开，给你完整的度量数据（advance、bearing），这正是第 5 章排版需要的。位图质量、hinting、抗锯齿都比 stb 强，是浏览器和大多数 Linux 桌面的底层引擎。注意它不做塑形——连字、字偶距要交给 HarfBuzz。

目标塑形 · 不画像素：把字符串 "Office" 塑形成「字形索引 + 位置」序列（自动处理 ffi 连字等），再交给 FreeType 渲染。

#include <hb.h>
#include <hb-ft.h>   // 与 FreeType 桥接

// 复用前面 FreeType 的 face，创建 HarfBuzz font
hb_font_t *hb_font = hb_ft_font_create(face, NULL);

// 1. 准备 buffer，放入要塑形的文字
hb_buffer_t *buf = hb_buffer_create();
hb_buffer_add_utf8(buf, "Office", -1, 0, -1);
hb_buffer_set_direction(buf, HB_DIRECTION_LTR);
hb_buffer_set_script(buf, HB_SCRIPT_LATIN);
hb_buffer_set_language(buf, hb_language_from_string("en", -1));

// 2. 塑形！处理连字(ffi)、字偶距、复杂文字
hb_shape(hb_font, buf, NULL, 0);

// 3. 取出每个字形的「索引」和「位置」
unsigned int n;
hb_glyph_info_t     *info = hb_buffer_get_glyph_infos(buf, &n);
hb_glyph_position_t *pos  = hb_buffer_get_glyph_positions(buf, &n);

float cursor_x = 0;
for (unsigned int i = 0; i < n; i++) {
    unsigned int gid = info[i].codepoint; // 是字形索引，不是码点！
    float xoff = pos[i].x_offset  / 64.0f;
    float adv  = pos[i].x_advance / 64.0f;

    // 用 gid 让 FreeType 渲染这个字形（注意是 Load_Glyph）
    FT_Load_Glyph(face, gid, FT_LOAD_RENDER);
    draw_glyph(face->glyph, cursor_x + xoff);
    cursor_x += adv;
}

hb_buffer_destroy(buf);

关键点：HarfBuzz 的输出里 info[i].codepoint 其实是字形索引（GID），所以渲染时要用 FT_Load_Glyph（按索引）而不是 FT_Load_Char（按字符）。"Office" 里的 ffi 会被合成一个连字字形，n 因此小于 6——这就是塑形的价值。

把三者串起来：一句话的完整流程

真实渲染一段文字时，三个库（外加 GPU）是这样接力的：

1

HarfBuzz 塑形 shape

"Office" → 字形索引序列 [O,f,fi,c,e] + 每个的 x_advance / offset
2

FreeType 栅格化 raster

对每个 GID 调 FT_Load_Glyph，得到灰度位图 + bearing
3

打包进图集 atlas

把位图缓存到一张大纹理，记录每个字形的 UV 区域
4

OpenGL 绘制 draw

按 HarfBuzz 给的位置，为每个字形画一个带 UV 的四边形
为什么不全用 stb 就好？
stb_truetype 也能查 cmap、栅格化，但它几乎不做塑形：连字、阿拉伯语连写、复杂的 OpenType 特性都处理不了。只渲染拉丁字母、对排版要求不高时，stb 一个文件就够；要做严肃的多语言排版，HarfBuzz + FreeType 才是标准组合（也是浏览器的选择）。
编译提示
stb_truetype：直接 #include，无需链接库。 FreeType：pkg-config --cflags --libs freetype2，或链接 -lfreetype。 HarfBuzz：链接 -lharfbuzz，要桥接 FreeType 再加 -lharfbuzz 的 hb-ft 部分（现代版本已内置）。

实战问答：在 OpenGL 里「高效又省事」地渲染文字

这是字体渲染里一个经典问题。把它讲清楚，正好把前面几章串起来。

一个很常见、但走偏了的做法
用 stb_truetype 把一整串文字渲染成一张图，再贴到一个 quad 上当纹理。能用，但是——文字一变就要重建整张纹理；每段文字都要各自维护一个 quad + 纹理；数量一多就很低效。

问题的根源是「以整串文字为单位」去做纹理：文字内容、尺寸、位置一变就得重做，而且无法复用——同一个字母 e 在不同句子里被反复光栅化、反复存。正确的拆法是「以单个字形为单位」。

✅ 标准答案：字形图集（Glyph Atlas）+ 批处理（Batching）
  1. 预先把要用的字形烤进一张大纹理（图集 / atlas）：每个字形光栅化一次，记下它在大图里的 UV 区域和度量。这正是第 7 章讲的图集。
  2. 渲染文字时不再重建纹理：只为每个字形生成一个带 UV 的小四边形，位置由 HarfBuzz/度量给出。
  3. 把一段（甚至整屏）文字的所有四边形合并成一次 draw call（批处理）。这就是第 8 章讲的「攒一大批顶点、一次画完」。
一句话：纹理只烤一次，文字变化只改顶点缓冲。这正是 LibGDX、浏览器、游戏引擎的通用做法。

还有几个绕不开的坑，也要答上

方案怎么做适合 / 代价
整串烤成纹理
（走偏的做法）		一段文字 → 一张纹理 → 一个 quad实现最简单；但不可复用、文字一变就重建、数量一多就爆。
字形图集 + 批处理
推荐		所有字形烤进一张图，按 UV 拼四边形，一次 draw call高效、可复用；放大到远超烤制尺寸会糊。
SDF / MSDF
要缩放就上这个		图集里存的不是像素，而是「到字形边缘的距离场」，着色器里按距离阈值出边缘一张小图就能任意缩放、还能描边/发光；MSDF 还能保住尖角。详见第 11 章。
直接矢量 GPU
如 Slug 库		着色器里直接对贝塞尔轮廓求覆盖，完全不要缓存纹理无限清晰、无图集；实现复杂，Slug 是商业库。
「像素完美」和「缩放」怎么兼顾？
普通图集是按某个字号烤死的：原尺寸最清晰，放大就糊。两条路：①多准备几档字号的图集，就近选用（最简单）；②用 SDF/MSDF，一张图任意缩放（见第 11 章）。注意：真要「像素完美」还涉及子像素定位，这也是「漂亮的文字渲染很难」的原因——能接受单一字体 + 固定几档字号时，预烤一切是最省心的。
本地化 / CJK：图集会不会爆？
会。ASCII 一百多个字形，烤进一张图轻轻松松；但中日韩有上万字形，全烤进一张图不现实。做法是动态图集（按需缓存）：谁出现了才把谁光栅化、塞进图集，满了就淘汰旧的。这正是操作系统和浏览器的策略——软件光栅化 + 贴到四边形 + 动态缓存。复杂排版（阿拉伯连写、连字）则继续交给 HarfBuzz。
📌 一句话总结
别以「整串文字」为单位贴纹理。以「字形」为单位：烤一张字形图集、用批处理一次画完；要缩放就上 SDF/MSDF（见第 11 章）；CJK/本地化就用动态图集按需缓存。塑形交 HarfBuzz、光栅化交 FreeType/stb、绘制交 OpenGL——这一整套，就是前面几章拼出来的答案。

问：HarfBuzz 塑形后拿到的 codepoint 字段，能直接传给 FT_Load_Char 吗？为什么？

看答案

不能。HarfBuzz 输出里的 codepoint 字段名虽叫 codepoint，装的其实是字形索引 GID（已经过 cmap + 塑形）。要用 FT_Load_Glyph(face, gid, ...) 按索引加载；FT_Load_Char 是按 Unicode 码点加载、会自己再查一次 cmap，传 GID 进去就错位了。
