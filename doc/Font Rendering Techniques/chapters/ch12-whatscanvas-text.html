字字体渲染原理
CHAPTER 12 · IMPLEMENTATION MAP

WhatsCanvas 文本管线：从能力到验证

前 11 章讲的是字体渲染的通用原理。这一章把它们落到 WhatsCanvas 当前实现：一段 UTF-8 文本如何经过字体解析、fallback、双向文本、OpenType shaping、跨平台栅格化、glyph atlas，再进入 GPU 绘制；以及这些能力如何被测试和诊断。

当前能力一览

FONT MODEL

字体注册与 fallback

  • 支持系统默认字体发现与默认 fallback chain。
  • FontFace 支持文件与内存字体注册。
  • 支持 TrueType Collection face index。
  • 支持按 family / weight / slant 做 face matching。
  • FontFallbackChain 定义字体解析顺序。
  • 字体可声明覆盖码点范围，用于 fallback 选择。
SHAPING

Unicode 与 OpenType

  • UTF-8 输入归一化与错误输入的可预测处理。
  • UAX #9 双向文本解析、视觉 run 排序。
  • HarfBuzz 可选接入，输出 glyph index、advance、offset。
  • 无 HarfBuzz 时走 simple shaping 与 kerning fallback。
RASTER

跨平台栅格化

  • FreeType 可选接入，负责 glyph lookup、metrics、kerning、alpha raster。
  • stb_truetype 保留为 dependency-free fallback。
  • 支持按 glyph index 栅格化，这是 shaping 输出进入绘制的关键。
  • 已具备字体表探测与 COLR/CPAL v0 图层合成路径。
GPU

glyph atlas 渲染

  • 栅格化字形打包进 GlyphAtlas。
  • Canvas 复用持久 GPU atlas 资源。
  • 支持 dirty-rect 增量上传与过量更新自动合并。
  • RGBA atlas 可承载彩色字体图层。

字体发现：从名字到可用 face

应用通常只会说“我要某个 family、某个 weight/slant”，但真实机器上装了哪些字体、每个字体文件里有哪些 face、 哪些码点能覆盖、默认 fallback 该怎么排，都是文本系统要解决的问题。字体发现就是把系统和用户注册字体整理成 可查询的 FontFace / FontDescriptor 集合。

font.discovery.flow
01
扫描来源
读取系统默认字体目录、内置默认 family，以及用户通过 file/memory 注册的字体。
02
解析 face
提取 family、style、weight、slant、TTC face index、字体表能力与可选覆盖范围。
03
建立索引
把同一 family 下的 regular/bold/italic 等 face 组织起来，支持按请求样式匹配。
04
默认 fallback
根据平台默认字体和常见文字系统建立回退顺序，避免缺字直接变成 tofu。
05
运行时解析
渲染文本时按 primary family、fallback chain、码点覆盖范围，拆成多字体 runs。
术语在 WhatsCanvas 中的含义
Font discovery发现系统默认字体和已注册字体，并把它们转换成可查询的 face/descriptor。
Face matching当请求 family + weight + slant 时，从候选 face 中选最接近的一项。
Fallback chain主字体缺字时继续尝试的字体顺序；它决定混排文本会被拆成哪些 font runs。
Coverage某个 face 能覆盖哪些 Unicode codepoint；有显式范围时优先使用，必要时再向 rasterizer 查询 glyph availability。
TTC index一个 .ttc 文件里包含多个 face，注册和缓存时必须把 collection face index 纳入 key。

从文本到 GPU 的真实路径

whatscanvas.text.pipeline
01
UTF-8 输入
验证并归一化文本，保留 source byte range，方便后续诊断与布局回溯。
02
字体解析
按 primary family 与 fallback chain 选择可覆盖当前码点的 face。
03
Bidi run
用 UAX #9 解析混排方向，得到逻辑顺序与视觉顺序之间的映射。
04
Shaping
HarfBuzz 或 simple shaping 产出 glyph index、advance、offset 与 byte mapping。
05
Raster
FreeType 或 stb 按 glyph index 生成 alpha/RGBA glyph bitmap 与度量数据。
06
Atlas
字形进入 atlas，记录 UV、dirty rect、cache stats 与 rebuild 状态。
07
DrawCommand
Canvas 提交 atlas quads，走图像/纹理批处理路径进入 OpenGL。
08
GPU 输出
片元着色器采样 glyph atlas，叠加 Paint 颜色、渐变、透明度与阴影效果。

哪些点值得特别记住

能力为什么重要
fallback segmentation不同字体覆盖不同码点，文本必须先分段再 shaping/raster，否则 CJK、拉丁、符号混排会出现缺字或度量错位。
glyph-index pathOpenType shaping 的结果是 glyph index，不是 Unicode codepoint；渲染器必须能直接栅格化 glyph index。
UAX #9阿拉伯语、希伯来语与拉丁数字混排时，视觉顺序和逻辑顺序不同，必须先解决方向再排字形。
dirty rect atlas新字形出现时只上传变化区域，避免每帧重传整张 atlas；长文本压力过大时再合并为一次大更新。
RGBA atlas彩色字体与 alpha 字形可以共用渲染路径，后续扩展 CBDT/SBIX/SVG/COLR v1 时不需要推翻 atlas 设计。
diagnostics字体注册失败、fallback 缺失、shaping/raster/atlas 失败都会进入诊断链路，方便定位文本为什么退回备用路径。

验证体系

CONFORMANCE

Unicode 官方数据

  • 接入 BidiTest.txt 与 BidiCharacterTest.txt。
  • 通过生成的 DerivedBidiClass 数据覆盖完整 bidi class 查询。
  • 区分快速子集与 exhaustive 模式，便于本地和 CI 取舍。
PIXEL

文本像素回归

  • 覆盖 alpha atlas、RGBA atlas、fallback、布局、阴影等文字相关路径。
  • 以像素输出保护渲染行为，避免“度量正确但画面变化”漏掉。
  • 只聚焦字体文本，避免和其它渲染分支互相污染。
PERF

缓存与性能观测

  • loaded face cache 有容量控制、清理、hit/miss/eviction 统计。
  • glyph atlas 暴露 dirty rect、collapse、rebuild 等状态。
  • 这些指标能帮助判断性能瓶颈在 shaping、raster 还是 GPU 上传。
一句话总结
WhatsCanvas 的文本系统已经从“能画 ASCII 文本”推进到了完整的工程管线：公开字体模型、跨平台栅格化、OpenType shaping、Unicode bidi、fallback segmentation、glyph atlas、彩色字体基础路径、诊断与回归验证都已经连起来。后续扩展的重点不再是推倒重来，而是在现有边界内继续增加 native adapter、更多彩色字体格式和更丰富的排版特性。
检查一下理解

问：为什么 shaping 之后必须支持按 glyph index 栅格化，而不能只按 Unicode codepoint 画字？

看答案

因为 shaping 会把字符序列转换成字体内部的 glyph 序列：一个字符可能变成不同形态，一个组合可能变成一个 glyph，连字也可能把多个字符合成一个 glyph。此时正确的显示单位已经是 glyph index，而不是原始 Unicode codepoint。
